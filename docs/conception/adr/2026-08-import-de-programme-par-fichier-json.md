# Import d'un programme par fichier JSON

> **Révision 2026-08-26** : le fichier `.manuel.json` optionnel est retiré (demande d'Antoine).
> Personne ne consommait le `cheminement_type` chargé (l'organigramme A1→H8 reste hand-encoded GEX-only), et le second sélecteur alourdissait l'écran pour un champ mort.
> `LocalProgram.manual`, `ImportError::{InvalidManualJson, EmptyManual}` et le second sélecteur de fichier sont supprimés ; une enveloppe `localStorage` qui porte encore un champ `manual` se restaure sans lui (tolérance d'inconnu de `persist::restore`).
> Le reste de la décision tient.

## Contexte

Le directeur du programme veut pouvoir publier un millésime corrigé (un `{code}-{semestre}.json`, éventuellement accompagné de son `.manuel.json`) sans attendre le prochain scrape ni republier de snapshot livré avec l'application.
L'étudiant doit pouvoir charger ce fichier depuis l'écran de choix de programme, à côté de l'import par URL déjà en place (ADR `2026-08-import-de-programme-via-proxy-cors`), et le voir rejoindre `gh.v1.programmes-locaux` comme n'importe quel programme importé (ADR `2026-08-programmes-locaux-en-localstorage`).

## Décision

- Le fichier `Program` est obligatoire; le `.manuel.json` est optionnel. `crate::import::build_local_program_from_json` (`crates/ui/src/import.rs`) valide les deux strictement avant tout enregistrement (BLD-1) : un `Program` qui ne désérialise pas → `ImportError::InvalidProgramJson`, un manuel fourni qui ne désérialise pas → `InvalidManualJson`, un manuel dont `cheminements_types` est vide → `EmptyManual`. Rien n'est construit tant qu'une étape échoue — jamais de plan à moitié chargé.
- La provenance « fichier local » est portée par un nouveau champ `origin: ProgramOrigin` (`Url` | `File`) sur `LocalProgram`, plutôt que par un type de provenance dédié ou par deux variantes distinctes de `LocalProgram`. Un import par fichier garde tous les champs existants : `source_url` porte le nom du fichier choisi, `proxy` reste une chaîne vide. Ce choix évite de dupliquer `LocalProgram` (et donc `data.rs`, `persist.rs`, `panel.rs`, `components/panel.rs`, qui le lisent déjà) pour une différence qui se résume à « d'où vient cette entrée ». `#[serde(default)]` sur `origin` fait qu'une enveloppe déjà en `localStorage`, écrite avant l'existence du champ, continue de se restaurer — comme `Url`, ce qu'elle était de fait.
- `LocalProgram` gagne aussi `manual: Option<core::ProgramManual>` (`#[serde(default)]`, même raison), pour porter le `cheminement_type` du fichier `.manuel.json` quand il est fourni. Le `cheminement_type` est conservé même si aucun consommateur ne le lit encore (l'organigramme A1→H8 reste hand-encoded GEX-only, cf. CLAUDE.md) : le lire est hors périmètre de cette tâche, mais la carte du programme importé nomme déjà les cheminements types qu'il porte (`panel::local_mark`), pour que l'import soit vérifiable au moment où il se produit.
- **Pas de règle « Scolarité préparatoire » réappliquée** : contrairement à `build_local_program` (import par URL, qui parse une page ulaval.ca brute et doit calculer la règle lui-même), un fichier `{code}-{semestre}.json` est écrit par le scraper — `cli.rs::add_preparatory_rules` y a déjà ajouté la règle. La réappliquer ici la dupliquerait. `build_local_program_from_json` ne fait donc que désérialiser, jamais calculer.
- Les erreurs suivent la même discipline ERR-1 que le reste de l'import (`present::present_import_error`) : ce qui a été refusé, en français, et ce que l'étudiant peut faire (« Ce fichier n'est pas un instantané de programme valide… », « Le fichier manuel ne contient aucun cheminement type… »).
- `LocalMark.source_url: String` devient `LocalMark.link: Option<String>` : `Some` pour un import URL (la carte garde son lien cliquable vers la page source), `None` pour un import fichier — il n'y a pas de page en ligne vers laquelle pointer, seulement un nom de fichier déjà repris dans le texte de provenance. `panel::local_mark` construit ce texte selon `entry.origin` : « Importé le … via corsproxy.io. » pour `Url`, « Importé le … depuis le fichier … » pour `File`, avec une phrase supplémentaire nommant les cheminements types quand `entry.manual` en porte.

## Alternatives rejetées

- **Un `enum ProgramOrigin` à deux variantes portant chacune ses propres champs de provenance** (`Url { source_url, proxy }` / `File { file_name }`) — aurait forcé à reformuler chaque lecteur existant de `LocalProgram.source_url`/`proxy` (`data.rs`, `persist.rs`, `panel.rs`) autour d'un `match`, pour un import fichier qui n'a en réalité qu'une différence de provenance, pas de forme.
- **Réutiliser `DataError`** (l'erreur du chargement du catalogue au démarrage) pour ces deux nouveaux cas — `DataError` nomme des fichiers *du dépôt* (`cours.json`, `meta.json`) chargés au boot; un import fichier est un geste étudiant ponctuel, non critique (BLD-1), qui doit rester dans la famille `ImportError` déjà présentée par `present_import_error` et déjà non bloquante pour le reste de l'app.
- **Tolérer un fichier `Program` partiel** (ne garder que les champs lisibles) — irait à l'encontre de « ne jamais avaler silencieusement une entrée non reconnue » : un programme partiellement chargé compterait faux sans que l'étudiant le sache. Le typage strict de `serde` est le validateur, comme pour les cours manuels (`build_manual_course`).
